# 开发工作流智能体 · 设计

> 这份文档记录我们讨论定下来的架构，以及为什么这么定。代码在 `packages/workbench/`。

## 1. 目标

一个能真的接需求、改代码、跑测试、开 PR 的软件开发工作流智能体，并且**每一步判断都能被审计**：谁做的决定、有多确定、花了多少钱、落在哪条泳道。

参照物是一张决策面板：10 类决策、三条泳道、一份成本台账、一个「等你决定」队列。那张图最值钱的不是可视化，是它**强迫把 agent 的判断变成可审计的记录**。

## 2. 三个核心命题

### 2.1 置信度只来自机器证据，绝不让模型自评

模型说「我有 90% 把握」不是证据。可信的只有四类：

| 来源 | 例子 | 落到哪个决策 |
|---|---|---|
| 规则命中强度 | grep 命中 1 个文件 = 0.94，命中 4 个 = 0.4 | `which_file` |
| 检索区分度 | top1 与 top2 的相似度差 | `which_file`、`which_skill` |
| 机器凭证 | 测试退出码、通过数、失败数、编译错误数 | `is_done`、`retry_or_stop` |
| 静态分析 | 改动文件数、行数、是否碰迁移/配置/密钥 | `diff_risk` |

允许模型输出判断的地方，只给**有界输出**：选择题、0–10 分。不接受开放式自评。

### 2.2 三条泳道，按「可信度 × 成本」分

```
conf ≥ 0.80          → code      精确规则，不烧 token
0.50 ≤ conf < 0.80   → frontier  交回前沿模型
conf < 0.50          → human     太不确定，别猜
任何不可逆动作        → human     无视置信度
```

最后一条是硬规则：**irreversible, never auto**。合并 PR、删分支、轮换密钥、发客户回复，永远停在人这里。

一个「零人工」的开发智能体不是好智能体，是定时炸弹。面板上那 22 个 `waiting` 是设计目标，不是缺陷。

### 2.3 面板是事件流的投影，不是状态

唯一真相是 append-only 的事件日志（`events.jsonl`，一行一个决策）。面板所有数字都是它的聚合：

| 面板元素 | 聚合 |
|---|---|
| forks | `count(distinct decision)` |
| decisions | `count(*)` |
| 泳道分流 % | `group by lane` |
| 花费 | `sum(costUsd)` |
| 置信度曲线 | 最近 40 条 `confidence` |
| 等你决定 | `lane=human and status=waiting` |

所以面板自己什么都不存。host 重启后显示「变少」而不是「撒谎」。

## 3. 十个决策

分两组，对应面板的左右两列。

**执行侧（做之前）**

| key | 问题 | 置信度来源 | 正常泳道 |
|---|---|---|---|
| `which_file` | 改哪个文件 | 命中数 | code |
| `which_tool` | 用哪个工具 | 路由表 | code |
| `retry_or_stop` | 重试还是停 | 重试次数 + 错误是否同类 | code |
| `is_done` | 真的干完了吗 | 测试退出码 | code |
| `keep_result` | 这版留不留 | diff 规模 + 测试 | code |

**风控侧（做的时候）**

| key | 问题 | 置信度来源 | 正常泳道 |
|---|---|---|---|
| `which_skill` | 调哪个技能 | 路由表命中 | code |
| `diff_risk` | 改动风险 0–10 | 静态分析 | code（产出分数） |
| `which_model` | 用哪个模型 | 难度评分 | frontier |
| `injection` | 输入是否夹带 | 规则 + 小模型扫描 | frontier → human |
| `ask_person` | 要不要问人 | 评审结论 + 不可逆性 | human |

注意 `ask_person` 的置信度语义是**「不靠人也能做完的把握」**。有未决问题时是 0.2（→ human），干净时是 0.9（→ code）。写反了就会把该问人的事直接放行。

十个决策里真正需要前沿模型的只有三个左右，其余都能用代码回答 —— 这是省钱的地方。

## 4. 事件 schema

一个决策一行 JSONL：

```json
{
  "id": "ev_m3k9x_ab12cd",
  "seq": 41,
  "ts": "2026-11-01T13:41:02.000Z",
  "decision": "which_file",
  "group": "work",
  "question": "改哪个文件",
  "value": "src/auth.ts",
  "confidence": 0.94,
  "lane": "code",
  "rule": "file:single-hit",
  "irreversible": false,
  "action": null,
  "runId": "run_418",
  "task": "修登录超时",
  "costUsd": 0,
  "status": "ok",
  "evidence": { "hits": 1 }
}
```

字段要点：

- `rule` 是证据规则的名字，不是自由文本。置信度错了要靠它追溯：是规则写错了，还是规则选错了。
- `action` 出现不可逆动作时会被白名单打上 `irreversible: true`，泳道强制 `human`。
- `costUsd` 单条累加；目前只有 frontier 泳道会产生非零值。
- `status`：`ok` / `waiting`（停在人工泳道）/ `failed`。

## 5. 数据流

```
任务/ticket
    │
    ▼
┌──────────────┐   10 类决策 + 证据规则
│  Router      │   （不烧 token）
└──────┬───────┘
       │  按置信度 + 不可逆性分流
   ┌───┼──────────────┬──────────────────┐
   ▼                  ▼                  ▼
 code              frontier            human
 确定性执行         模型判断            停下等人
   └───┴──────────────┴──────────────────┘
                      │
              ┌───────▼────────┐
              │ events.jsonl   │  追加写，唯一真相
              └───────┬────────┘
                      │  GET /workbench/state（只读）
                      ▼
              ┌────────────────┐
              │ 决策面板        │  投影，不存状态
              └────────────────┘
```

## 6. 三种失败模式与兜底

| 失败 | 表现 | 兜底 |
|---|---|---|
| 路由错 | 该问人的没问，直接写库 | 不可逆白名单 + 预算熔断 |
| 死循环 | 反复改同一文件不收敛 | 重试上限 → 强制升级 / 强制转人工 |
| 幻觉 | 模型说「测试过了」实际没过 | **只信机器凭证，不信自我报告** |

第三条是命门。agent 说 done 不算 done，测试退出码才算。

## 7. 落地阶段

| 阶段 | 内容 | 状态 |
|---|---|---|
| **P0** | 事件日志 + 路由器 + 只读状态路由 + 决策面板 | ✅ 已完成 |
| **P1** | code 泳道真执行（定位 → 改 → 测 → diff）、人工审批队列 | ⬜ 待做 |
| **P2** | 泳道图、置信度曲线、成本台账、审批时间线 | ⬜ 待做 |

P0 先做的理由：那张图里好看的部分（连线、粒子、发光）只是最后 10% 的工作量。前面 90% 是「把隐性判断变成显式记录」——这步做完，用什么看都行。

## 8. 已知缺口

- `build` 阶段声明了但没实现：现在只记录决策，没有执行器。
- 成本只有单条 `costUsd`，还没从 llm 调用里真实收集 token 花费。
- 人工审批只能在面板上看，还不能在面板里点「批准」。
- 置信度规则是启发式，不是概率。命名成 `rule` 就是为了事后能查是规则错了。

## 9. 为什么不用另一种做法

**「所有阶段都交给大模型」**：每个阶段烧一轮模型，贵、慢、且不可审计。图的原话是 *answered without a thinker* —— 第 5 节那个 Router 存在的全部意义就是不烧 token。

**「工具和阶段尽量多给」**：工具越多，模型选错的概率越高。10 个决策、少而准的工具，比 30 个决策的「全能助手」好用。
